# Журнал поиска: ui

Ход поиска подхода: вопрос, гипотеза, условия замера, числа, вывод. Новые записи сверху. Подтверждённые выводы переносятся в [`../decisions/ui.md`](../decisions/ui.md).

## 2026-10-29 — размер страницы с React

**Статус:** замерено, решение «Интерфейс на React» уже принято → [`../decisions/ui.md`](../decisions/ui.md#интерфейс-на-react)

**Вопрос.** Насколько React увеличивает страницу. В решении это было записано как «не измерено».

**Условия замера.** Один прогон, размер детерминирован. Байты — `wc -c`, сжатие — `gzip -c` (Apple gzip 487.0.1) с уровнем по умолчанию. Код до перехода — коммит `fecb0ff`. Сборка Vite 8.3.5 с минификацией по умолчанию; старая сборка esbuild была без минификации.

**Результат.**

| Сборка | Байт | gzip, байт |
|---|---|---|
| До: esbuild, без React (`fecb0ff`, `dist/camera-calc.html`) | 223 678 | 58 153 |
| Тот же код, сборка Vite | 160 201 | 47 372 |
| Шаг 1 #65: Vite, React 19.3.1, вкладки на React, стили в `src/styles.css`, каркас с doctype (`dist/index.html`) | 379 589 | 115 083 |
| Конец #65: весь `ui` на React, формулы импортом `?raw` (`dist/index.html`) | 380 324 | 115 308 |

**Вывод.** React с `react-dom` добавляет около 219 КБ, после сжатия — около 68 КБ (разница второй и третьей строки). Минификация Vite снимает около 63 КБ по сравнению со старой сборкой. После перехода всего `ui` страница почти не изменилась: +735 байт, после сжатия +225 байт к шагу 1. Время загрузки страницы с GitHub Pages не замеряли.

## 2026-10-29 — сколько кода занимает ручное обновление DOM

**Статус:** принято → [`../decisions/ui.md`](../decisions/ui.md#интерфейс-на-react)

**Вопрос.** Продолжение записи от 2026-10-28: интерфейс разложен по файлам `src/ui/` (#50), можно посчитать ручную работу с DOM и решить по правилу выбора инструментов, нужен ли фреймворк.

**Гипотеза.** Ручная работа сосредоточена в нескольких функциях отрисовки, а большая часть кода — шаблонные строки разметки, которые во фреймворке остались бы почти такими же (JSX вместо строки). Тогда фреймворк сократит немного кода, а переписать придётся весь `ui`.

**Условия замера.** Код `src/ui/*.ts` и `src/main.ts` в ветке `refact/50-ui-files`, подсчёт `grep` и `wc -l` по исходникам, один прогон (подсчёт детерминированный). Прототип на фреймворке не писали, поэтому объём кода после перехода не измерен.

**Результат.**

| Что | Число |
|---|---|
| Строк в `src/ui/` и `src/main.ts` | 1703 |
| Присваиваний `innerHTML` | 30, из них 12 в `system-panel.ts`, 6 в `type-result.ts` |
| Вызовов `addEventListener` в коде | 40 |
| Функций, которые пересоздают разметку и навешивают обработчики заново | 5: `renderObjects` (75 строк), `renderTabs` (34), `renderGpuView` (36), `renderCamView` (26), `renderDetView` (36) — всего 207 строк, 10 вызовов `addEventListener` |
| Присваиваний свойств элементов (`textContent`, `hidden`, `className`, `value`, `checked`, `disabled`, `readOnly`, `placeholder`) | 80 |
| Обращений к элементу по id (`byId`) | 123 |

Ручную синхронизацию поля формы и состояния ведут `writeForm`, `readForm`, `syncFormUI` (`type-form.ts`, `object-cards.ts`) и `writeSystemForm` (`system-panel.ts`). Схема (`side-diagram.ts`, 195 строк) и кольца (`ring` в `system-panel.ts`) — расчёт координат SVG. Во фреймворке он остался бы тем же кодом.

**Вывод.** Фреймворк убрал бы повторное навешивание обработчиков в 5 функциях (10 мест) и часть из 80 присваиваний свойств: их заменило бы связывание полей с состоянием. Шаблоны разметки, расчёт координат схемы и колец, отчёт, подсказки и маршрутизация от фреймворка не сокращаются. Цена фреймворка: новая зависимость в коде страницы, синтаксис компонентов (JSX или шаблоны) и переписывание всех 1703 строк. На эти числа правило выбора инструментов (выигрыш перевешивает цену зависимости) не выполняется. Рекомендация была не подключать фреймворк. Владелец решил иначе: главный критерий — качество кода и общеизвестные отлаженные решения вместо своих, поэтому выбран React (см. решение).

**Дальше.** Вернуться к вопросу, если число функций, которые пересоздают разметку с обработчиками, заметно вырастет (новые экраны) или появятся ошибки рассинхронизации поля и состояния.

## 2026-10-28 — нужен ли фреймворк интерфейса

**Статус:** не проверял

**Вопрос.** Интерфейс обновляется вручную: `innerHTML` и навешивание обработчиков заново после каждой отрисовки. Подключать ли фреймворк при переходе на новую структуру.

**Варианты.**

- Без фреймворка: файлы в `src/ui/` по экранам и блокам, отрисовка по состоянию из `app`. Нет зависимостей, способ отрисовки не меняется.
- Небольшой фреймворк (Preact, Lit, Svelte): обновление DOM по изменению состояния, обработчики не навешиваются вручную. Новая зависимость в коде страницы, новый синтаксис компонентов, переписывается вся отрисовка.

**Гипотеза.** Перестройку структуры и смену способа отрисовки лучше не совмещать: тест-эталон проверяет страницу целиком, и при двух изменениях сразу непонятно, какое из них сломало результат. Фреймворк, если понадобится, подключается после перехода, к готовым `domain` и `app`.

**Дальше.** Вернуться к вопросу после разделения `ui` по файлам: посчитать, сколько кода занимает ручное обновление DOM и навешивание обработчиков, и выбрать по правилу выбора инструментов из [`ARCHITECTURE.md`](../ARCHITECTURE.md#выбор-инструментов).
