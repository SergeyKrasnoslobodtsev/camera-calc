# Решения: build

Итог по сборке и проверкам: что действует, что отброшено, что осталось открытым. Ход поиска — в [`../discussions/build.md`](../discussions/build.md).

## Принятые решения

### Публикация на GitHub Pages через GitHub Actions

**Статус:** принято владельцем проекта 2026-10-29, сделано в #66.

**Контекст.** Собранная страница `dist/index.html` хранилась в репозитории, чтобы её можно было открыть без сборки, и её нужно было пересобирать и коммитить после каждой правки в `src/`. Страница — один файл без внешних ресурсов, кроме шрифтов.

**Решение.** Решаем: страницу публикует на GitHub Pages workflow `.github/workflows/static.yml` при push в `main`: `npm ci`, `npm test`, `npm run build`, затем `actions/upload-pages-artifact` с папкой `dist` и `actions/deploy-pages`. `dist/` добавлен в `.gitignore` и удалён из репозитория. Изменения попадают в `main` из `dev` отдельным слиянием.

**Последствия.**

- Хорошо: в коммитах нет собранного файла, правка в `src/` не требует пересборки; страница публикуется только после прохождения тестов.
- Плохо: открыть страницу без сервера можно только после `npm run build`; в репозитории готового файла нет.
- Нейтрально: сайт обновляется только при слиянии в `main`, а не в `dev`. В окружении `github-pages` публикация разрешена из `main`.

**Подтверждение.** Первый запуск на `main` после слияния PR #75 (2026-10-29): задания `build` и `deploy` прошли. По адресу https://sergeykrasnoslobodtsev.github.io/camera-calc/ сервер отдаёт собранный `index.html` (380 875 байт) без ссылки на `/src/main.tsx`, исходники не публикуются (`package.json` — 404). Chrome без окна отрисовал страницу: заголовок, вердикт, кнопка языка.

### Сборка модулей esbuild в один HTML

**Статус:** заменено решением «Сборка на Vite в один HTML» (2026-10-29). Было принято 2026-10-28, переход на модули — #32. Выбрано по правилу выбора инструментов из [`ARCHITECTURE.md`](../ARCHITECTURE.md#выбор-инструментов). Сравнение вариантов и замер — в [`../discussions/build.md`](../discussions/build.md).

**Контекст.** `build.py` склеивает файлы `src/js/*.js` в порядке имён в один `<script>` и вставляет его в `src/layout.html` вместе с блоком формул. Поэтому код живёт в одной глобальной области, а порядок файлов задают числовые префиксы. Для `import` и `export` нужен сборщик. Результат по-прежнему должен быть одним файлом `dist/camera-calc.html`, который открывается без сервера. Сейчас для работы нужны два языка: Python для сборки и Node для тестов.

**Решение.** Решаем: модули собирает esbuild (формат `iife`, один скрипт) из точки входа: сейчас `src/js/init.js`, после перестройки `src/main`. Сборку выполняет скрипт `build.ts` на Node вместо `build.py`: он вызывает esbuild и вставляет разметку, формулы и скрипт в `dist/camera-calc.html`. esbuild подключается как зависимость разработки.

**Последствия.**

- Хорошо: зависимости между модулями видны в `import`; для сборки и тестов нужен только Node.
- Плохо: новая зависимость; сборка требует `npm install`.
- Нейтрально: `npm run build` по-прежнему одна команда.

**Подтверждение.** `dist/camera-calc.html` собирается одним файлом и открывается из файловой системы; `npm test` проходит; `tests/golden.txt` не меняется.

### Сборка на Vite в один HTML

**Статус:** принято владельцем проекта 2026-10-29, сделано в #65 (шаг 1). Замер — в [`../discussions/build.md`](../discussions/build.md#2026-10-29--сборка-и-линтер-для-интерфейса-на-react).

**Контекст.** Интерфейс переходит на React (решение «Интерфейс на React» в [`ui.md`](ui.md#интерфейс-на-react)). Своя сборка `build.ts` склеивает разметку, формулы и скрипт строками. Владелец хочет, чтобы проект выглядел привычно для разработчиков на React и публиковался на GitHub Pages (#66). Страница должна оставаться одним файлом, который открывается без сервера.

**Решение.** Решаем: страницу собирает Vite с плагинами `@vitejs/plugin-react` и `vite-plugin-singlefile` по `vite.config.ts`. Исходная страница — `index.html` в корне проекта: doctype, `<head>` с `charset` и `viewport`, разметка и `<script type="module" src="/src/main.tsx">`. Стили — в `src/styles.css`, их подключает `main.tsx`, Vite встраивает их в страницу. Формулы вставлял в блок `#formulas` плагин `formulas` из `vite.config.ts`; в #65 блок формул стал частью компонента, и владелец выбрал импорт текстов как строк (`?raw`) в `CalculationPage.tsx` — плагин удалён. Результат — `dist/index.html`. `build.ts` и зависимость `esbuild` удалены.

**Последствия.**

- Хорошо: сборка описана стандартной конфигурацией вместо своего скрипта; `npm run dev` даёт сервер разработки, где правка видна без пересборки; скрипт минифицируется.
- Плохо: больше зависимостей разработки; jsdom не выполняет `<script type="module">`, поэтому тесты страницы запускают скрипт сами (`tests/page.js`) и ждут отрисовку React. Это уйдёт с переходом тестов на Vitest (#67).
- Нейтрально: страница называется `dist/index.html` вместо `dist/camera-calc.html`, чтобы на GitHub Pages открываться по корневому адресу.

**Подтверждение.** `npm run build` собирает один файл; `npm test` проходит, `tests/golden.txt` не изменился; `dist/index.html` по `file://` в Chrome 156 отрисовал вкладки и вердикт без ошибок JavaScript (2026-10-29).

До перехода у страницы не было doctype, поэтому браузер рисовал её в режиме совместимости (quirks mode). Скриншоты `file://` в Chrome 156 на ширине 1300, 900 и 390 px до и после добавления doctype различаются только таблицами: в режиме совместимости таблицы не наследуют размер шрифта, теперь берут его из CSS.

### Линтер Oxlint

**Статус:** принято владельцем проекта 2026-10-29, подключено в #65 (шаг 1). Замер — в [`../discussions/build.md`](../discussions/build.md#2026-10-29--сборка-и-линтер-для-интерфейса-на-react).

**Контекст.** В компонентах React есть правила, которые `tsc` не проверяет: хуки вызываются без условий и в одном порядке, зависимости эффектов перечислены полностью. Обычно их проверяет ESLint с `eslint-plugin-react-hooks` и `typescript-eslint`. Проект использует TypeScript 7.0.2, а `typescript-eslint` 8.72.1 поддерживает `typescript` только до 6.1 и опирается на JavaScript API, которого в TypeScript 7 нет.

**Решение.** Решаем: код проверяет Oxlint (`npm run lint`, настройки — `.oxlintrc.json`): категория `correctness` — ошибки, `react/rules-of-hooks` — ошибка, `react/exhaustive-deps` — предупреждение.

**Последствия.**

- Хорошо: правила хуков проверяются без отката TypeScript; Oxlint не зависит от пакета `typescript`.
- Плохо: менее распространён, чем ESLint; правил, которым нужны типы, у него нет.
- Нейтрально: на коде до перехода на React Oxlint находит 12 замечаний (см. «Известные проблемы»).

**Подтверждение.** На пробном компоненте `rules-of-hooks` дал ошибку на условный `useState`, `exhaustive-deps` — предупреждение. В `npm test` линтер пока не входит.

### Тесты на Vitest и React Testing Library

**Статус:** принято владельцем проекта 2026-10-29, сделано в #67. Подход выбрал владелец: «общепринятые практики», тесты разложены по папкам и темам. Заменяет решение «Юнит-тесты ядра на `node:test`». Замер — в [`../discussions/build.md`](../discussions/build.md#2026-10-29--тесты-на-vitest-и-react-testing-library).

**Контекст.** Тесты `domain` написаны на `node:test`. Тесты страницы открывают собранный `dist/index.html` в отдельных окнах JSDOM, сами выполняют модульный скрипт (`tests/page.js`) и ждут отрисовку React (`settle`). Тест страницы занимал один файл на 725 строк, и проверки в нём зависели от порядка: сохранение, которое готовили первые, использовали следующие. Для проекта на Vite и React привычны Vitest и Testing Library.

**Решение.** Решаем: все тесты запускает Vitest (`npm test` = `tsc && vitest run`). Тесты страницы отрисовывают `App` из исходников через `render` из `@testing-library/react` в окружении jsdom (строка `// @vitest-environment jsdom` в начале файла). Действия выполняются через `fireEvent`: он оборачивает событие в `act`, и React отрисовывает изменения сразу. Новое открытие страницы (`tests/page/open-page.tsx`) размонтирует прежнюю, сбрасывает модули (`vi.resetModules`), записывает сохранение и язык в `localStorage` и запускает приложение так же, как `src/main.tsx`: подготовка до отрисовки вынесена в `src/start.ts`. Тест-эталон сравнивает результат с `tests/golden/golden.txt` через `toMatchFileSnapshot`. Тесты разложены по папкам: `domain/`, `i18n/`, `page/` (по темам), `golden/`. Каждый файл самостоятельный.

**Последствия.**

- Хорошо: сборка перед тестами не нужна, обходы `runModuleScripts` и `settle` убраны; ошибка показывает тест и файл темы; файлы не зависят друг от друга; эталон обновляется стандартным `vitest -u`.
- Плохо: тесты проверяют исходники, а не собранный `dist/index.html`. Ошибку сборки (плагин Vite, встраивание скрипта) тесты не заметят, её видно только при открытии страницы. Окно jsdom одно на файл: страницы открываются по очереди, а значения, которые сравниваются между страницами, тест запоминает заранее. Перезагрузку страницы тест видит только по сообщению jsdom на `jsdom.virtualConsole`.
- Нейтрально: три новые зависимости разработки (`vitest`, `@testing-library/react`, `@testing-library/dom`). Проверки написаны на `node:assert`, как раньше, а не на `expect`.

**Подтверждение.** `npm test` проходит: 116 тестов в 14 файлах. Тесты `domain` — 92, как на `node:test`. В тестах страницы и словарей 64 вызова `assert`, как в `tests/smoke.test.js`. MD5 `tests/golden/golden.txt` не изменился. Тест-эталон падает, если в эталоне поменять одно число.

### TypeScript и проверка типов `tsc`

**Статус:** принято 2026-10-28, проверка типов в `npm test` — #46. Выбрано по правилу выбора инструментов из [`ARCHITECTURE.md`](../ARCHITECTURE.md#выбор-инструментов). Сравнение вариантов — в [`../discussions/build.md`](../discussions/build.md).

**Контекст.** Поля сущностей (GPU, камера, детектор, тип камер, объект) нигде не описаны целиком, их видно только по местам использования. esbuild собирает `.ts` без отдельного шага компиляции. Node v26.12.1 запускает тесты `node:test` из `.ts` файлов без флагов (проверено на тестовом файле 2026-10-28). Типы esbuild и Node не проверяют, только убирают.

**Решение.** Решаем: код пишется на TypeScript. Типы сущностей объявляются в `src/domain/entities/`. `tsc --noEmit` проверяет типы в составе `npm test`. Файлы переводятся с `.js` на `.ts` по мере переноса в новые папки, а не все сразу.

**Последствия.**

- Хорошо: поля каждой сущности описаны в одном месте, ошибки в именах и типах полей находятся до запуска; запись типов короче, чем комментарии JSDoc.
- Плохо: `typescript` нужен как зависимость разработки; синтаксис типов надо читать и писать.
- Нейтрально: на время перехода в коде одновременно есть `.js` и `.ts` файлы.
- Нейтрально: esbuild читает `strict` из `tsconfig.json` и начинает собранный скрипт с `"use strict"`. Исходники — ES-модули, а модули по стандарту выполняются в строгом режиме, поэтому страница работает так, как написан код.

**Подтверждение.** `npm test` запускает `tsc` (`noEmit` задан в `tsconfig.json`) и падает при ошибке типа: опечатка `outputFiles[0].txt` в `build.ts` дала `TS2551` и код выхода 1. Без опечатки `npm test` проходит, `tests/golden.txt` не изменился. Ошибку в поле сущности проекта не проверяли: сущностей на TypeScript пока нет.

### Тесты проверяют страницу, а не глобальные переменные

**Статус:** предложено. Целевая структура одобрена владельцем 2026-10-28.

**Контекст.** Тесты открывают `dist/camera-calc.html` в jsdom и в 18 местах читают глобальные переменные страницы через `eval`: `report`, `snapshot()`, `RU`, `EN`, `STR.tips`, `priceOf`, `gpuById` (`tests/golden.test.js`, `tests/smoke.test.js`). После сборки модулей в один скрипт этих глобальных переменных не будет.

**Решение.** Решаем: тесты страницы получают данные так, как их видит пользователь. Отчёт берут через кнопку «Копировать отчёт», подменив буфер обмена. Состояние берут из `localStorage`, цены — из таблицы каталога. Словари и функции `domain` тесты импортируют напрямую. Сначала тесты переводятся на это при старом коде, и только потом меняется сборка, чтобы тесты и код не менялись в одном шаге.

**Последствия.**

- Хорошо: тесты не зависят от внутреннего устройства кода и переживают его перестройку.
- Плохо: проверка словарей не переедет до перехода на модули, потому что до него их нельзя импортировать.
- Нейтрально: `tests/golden.txt` не меняется, меняется только способ сбора данных для сравнения.

**Подтверждение.** В `tests/` нет `eval(`; `npm test` проходит; `tests/golden.txt` не меняется.

### Юнит-тесты ядра на `node:test`

**Статус:** заменено решением «Тесты на Vitest и React Testing Library» (2026-10-29). Было: предложено. Целевая структура одобрена владельцем 2026-10-28.

**Контекст.** Сейчас всё проверяется только через страницу в jsdom. Расчёт после выноса в `domain` можно вызывать напрямую.

**Решение.** Решаем: тесты `domain` пишутся на встроенном модуле `node:test` и запускаются из `npm test`, без jsdom и без сборки.

**Последствия.**

- Хорошо: новых зависимостей нет; ошибка в расчёте указывает на функцию, а не на текст страницы.
- Плохо: возможностей у `node:test` меньше, чем у отдельных библиотек тестирования.
- Нейтрально: тест-эталон остаётся проверкой всей страницы.

**Подтверждение.** `npm test` запускает юнит-тесты `domain`.

Проверка выполнена (#35): `npm test` запускает `node --test tests/domain/`, тесты идут без jsdom и без сборки.

## Известные проблемы

### Тесты зависят от глобальных переменных страницы

**Статус:** снято решением «Тесты проверяют страницу, а не глобальные переменные»: в `tests/` нет `eval(` (#45, #32).

18 вызовов `eval` в `tests/golden.test.js` и `tests/smoke.test.js` перестали бы работать после перехода на модули (#32).

### Замечания Oxlint в старом коде

**Статус:** решено 2026-10-29 (#68). Линтер входит в `npm test`.

`npm run lint` находил 12 замечаний в коде до перехода на React, после перехода — 9:
- неиспользуемый параметр `catch` в `src/app/persistence.ts` и `src/i18n/index.ts` — заменён на `catch {}`;
- переменные `nvdec`, `price`, `blurPx` в `tests/domain/entities.test.ts` — это деструктуризация с `...rest`, которой из объекта убирают поле. В `.oxlintrc.json` для `no-unused-vars` включён `ignoreRestSiblings`, тесты не менялись;
- `unicorn/no-thenable` в `tests/page/helpers.js`: заглушка файла нарочно возвращает синхронный `then`, чтобы проверки после импорта шли без ожидания. Правило отключено для этой строки комментарием.

## Отброшенные альтернативы

### ESLint с `typescript-eslint`

**Статус:** отброшено 2026-10-29. Не работает с TypeScript 7.0.2: `typescript-eslint` 8.72.1 требует `typescript <6.1` и JavaScript API, которого в TypeScript 7 нет. Пересмотреть, если `typescript-eslint` начнёт поддерживать TypeScript 7 или проект откатится на TypeScript 5.9.
