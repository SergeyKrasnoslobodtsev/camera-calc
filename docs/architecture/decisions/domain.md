# Решения: domain

Итог по модулю: что действует, что отброшено, что осталось открытым. Ход поиска — в [`../discussions/domain.md`](../discussions/domain.md).

## Принятые решения

### Расчёт без DOM, без текстов и без глобального состояния

**Статус:** принято 2026-10-28. Расчёт вынесен в `src/domain/` и прошёл проверку из раздела «Подтверждение».

Для расчёта типа камер и справочников проверка выполнена (#35): `src/domain/compute-type/` и `src/domain/references/`, тесты `tests/domain/` проходят в `npm test`, `tests/golden.txt` не изменился. Для подбора GPU и итогов системы — тоже (#47): `src/domain/compute-system/`, тесты `tests/domain/compute-system.test.ts`, `tests/golden.txt` не изменился. Тип камер и параметры системы приходят в расчёт разобранными, числами (#58). В интерфейсе пока остаются производные для отрисовки: статистика объектов, ёмкость декодера для шкалы, доли запусков на кольце. Отличие от формулировки ниже: у заметок-советов (`downscale`, `resolution`, `resolutionNone`) и у вердикта в `values` есть ссылка на объект того же результата, а у `resolution` — запись разрешения; так текст берёт имя и размеры объекта без поиска по номеру.

**Контекст.** `computeType` (`src/js/04-compute-type.js`) не обращается к DOM, но возвращает готовые фразы: описание подачи (`t("feedTiles", …)`), заметки, заголовок вердикта, функции `sensorPxText` и `modelPxText`. Он берёт данные из глобальных переменных через `cameraById` и `RESOLUTIONS`, а `RESOLUTIONS` собираются через `t()` (`src/js/01-data.js`). `computeSystem` (`src/js/05-system-ui.js`) сам читает поля формы `efficiency`, `reserve`, `gpu`, `gpuCount` и возвращает переведённое узкое место. Суммарный поток, стоимость камер и выбор сетевого порта считаются внутри отрисовки `renderSystem`. Из-за этого расчёт нельзя вызвать из Node без jsdom, а смена языка задевает расчёт.

**Решение.** Решаем: функции `domain` получают всё, что им нужно, аргументами и возвращают числа и коды. Статус объекта — `"ok" | "warn" | "bad"`. Заметка — `{ code, values }`, где `values` — числа, а не отформатированные строки. Справочники — массивы объектов с именованными полями. У встроенных записей вместо имени ключ, по которому `ui` берёт текст из `i18n`. Итоги системы (поток, стоимость камер, порт, PoE, архив) считаются в `domain`. Константы формул (0,8 ГБ базовой памяти, 20 кадров на поток, 15,4 Вт на порт PoE и другие) объявляются именованными константами с источником рядом.

**Последствия.**

- Хорошо: расчёт тестируется в Node без jsdom; язык и формат чисел не влияют на результат расчёта.
- Плохо: тексты заметок и вердикта переезжают в `ui` и `i18n`, нужен перевод кодов. Этот код раньше был внутри `computeType`, теперь он отдельно.
- Нейтрально: форма результата `computeType` меняется, и все места, где он читается, переписываются.

**Подтверждение.** В `src/domain/` нет `document`, `window`, `localStorage` и импортов из `i18n`, `app`, `ui` (проверка `grep` в тестах). Юнит-тесты `domain` на `node:test` запускаются без jsdom. `tests/golden.txt` не меняется.

### Одна функция разбора на сущность

**Статус:** принято 2026-10-29. Формы шаблонов, загрузка из `localStorage` и импорт файла пользуются одними функциями разбора (#48).

Тип камер, объект и параметры системы хранятся черновиком (решение «Черновик формы отдельно от проверенных значений» в [`app.md`](app.md)). Их функции разбора переводят числа черновика в `value`, и расчёт принимает только `value` (#58). Store и сохранение остаются при черновике. Недопустимое число в черновике даёт ошибку поля, а не подстановку (#36): см. решение «Недопустимое число в черновике — ошибка, а не подстановка».

**Контекст.** Одна и та же сущность проверяется в нескольких местах по разным правилам (см. «Известные проблемы»). Числовые параметры хранятся строками из формы, и разбирает их `computeType` во время расчёта (`parseNum` в `src/js/04-compute-type.js`). При ошибке он часть значений молча заменяет, например запас кадра через `|| 0`.

**Решение.** Решаем: у каждой сущности (GPU, камера, детектор, тип камер, объект, параметры системы) свой файл в `src/domain/entities/` с функцией `parse<Сущность>(raw)`. Она возвращает `{ ok: true, value }` или `{ ok: false, errors }`, где `errors` — список `{ field, code }`. В `value` попадают только известные поля, уже числами. Форма, загрузка из `localStorage` и импорт файла вызывают одну и ту же функцию. Расчёт принимает только `value`.

**Последствия.**

- Хорошо: правило для поля записано один раз; ошибочные данные из файла не доходят до расчёта.
- Плохо: где правила сейчас расходятся, поведение на недопустимых данных изменится. Загрузка и импорт станут строже, как форма. Эталон этого не покажет, потому что в нём только допустимые конфигурации.
- Нейтрально: тихие подстановки в расчёте убираются вместе с переходом. Что показывать вместо них, решается в #36.

**Подтверждение.** Юнит-тесты на каждую функцию разбора: допустимые данные, каждое правило поля, лишние поля. Тест: файл импорта с GPU без цены отклоняется.

### Недопустимое число в черновике — ошибка, а не подстановка

**Статус:** принято 2026-10-29. Выбор владельца в задаче #36.

**Контекст.** Разбор черновика молча заменял часть значений: пустое число камер — 0, дробное — округлял, пустые запас кадра, перекрытие тайлов, запас по нагрузке и глубину архива — 0, отрицательный запас — 0. Неверная цена GPU заменялась ценой из каталога. Отрицательные числа нигде не отсекались. Поля формы — `type="number"`: браузер превращает нечисловой ввод (например, «1e») в пустую строку, поэтому с подстановкой опечатка становится нулём без следа. Браузер проверяет `min` и `step` сам и подсвечивает поле `:invalid`, но эта проверка есть только у полей на экране, а не у черновиков из сохранения и импорта.

**Решение.** Решаем: правила проверяет только разбор (`parse*`), подсветка браузера на расчёт не влияет. Правила черновика:

- любое число не меньше 0 (`nonNegative`); пустое или нечисловое значение поля, которое нужно не всегда (фокус, угол, ширина матрицы, размеры объекта), остаётся `NaN`, и его отсекает расчёт, если поле используется;
- число камер, запас кадра, перекрытие тайлов, запас по нагрузке, глубина архива обязательны: пустое — ошибка; доля производительности GPU больше 0;
- целые (`integer`): число камер, глубина архива, у шаблонов — кадр камеры `Nw`, `Nh` и число NVDEC.

Если ошибки разбора — только в значениях чисел (`positive`, `nonNegative`, `integer`, функция `onlyValueErrors`), загрузка и импорт сохраняют черновик как есть, а расчёт показывает ошибку ввода. Ошибка другого вида (нет поля, значение не из списка) по-прежнему отклоняет запись. Правка цены GPU, которая не больше 0, — ошибка: подбор GPU не выполняется.

**Последствия.**

- Хорошо: опечатка или отрицательное значение видны как «Ошибка ввода» во вкладке, вердикте и отчёте, в том числе для данных из сохранения и импорта.
- Плохо: чтобы отключить архив или запас, нужно ввести 0: пустое поле теперь ошибка. Сохранения с пустыми полями, которые раньше давали 0, после загрузки показывают ошибку. Нечисловой ввод в поле, которое в текущем режиме не используется (например, фокус при подборе «авто»), браузер подсвечивает, а расчёт не считает ошибкой.
- Нейтрально: интерфейс показывает общий текст ошибки, без списка полей. Фикстура `tests/domain/fixtures/compute-type.json` не меняется: два её случая с числом камер «2.6» и «» тест проверяет как ошибку разбора.

**Подтверждение.** Юнит-тесты `tests/domain/entities.test.ts` на каждое правило. `tests/smoke.test.js`: у каждого `input[type=number]` есть `min="0"`; число камер 1.5 и высота −1 дают ошибку ввода в вердикте и отчёте, в том числе после загрузки из сохранения; пустая доля, отрицательный запас, пустая и отрицательная цена GPU дают ошибку в блоке подбора и в отчёте; камера с дробным кадром не добавляется.

### Функции разбора вручную, без библиотеки схем

**Статус:** принято 2026-10-29. Выбор владельца по замеру из [`../discussions/domain.md`](../discussions/domain.md), запись 2026-10-29.

**Контекст.** Функции разбора можно писать вручную или описать схемой библиотеки, например Zod. Библиотека попадает в код страницы, а страница — один файл `dist/camera-calc.html` (до перехода — 208 746 байт). Правила полей простые: обязательное, число больше нуля, число не меньше нуля, значение из списка, порядок двух значений. Есть два правила с условием: декодер GPU задаётся потоками у Jetson и числом NVDEC у остальных, фокус «от» не больше «до».

**Решение.** Решаем: функции `parse*` пишутся вручную. Общие правила полей — в `readFields` (`src/domain/entities/parse-result.ts`): значение поля возвращается, нарушение копится в списке ошибок `{ field, code }`. Функция сущности — список полей с правилом у каждого.

**Последствия.**

- Хорошо: нет зависимости в коде страницы. `zod/mini` добавил бы 15,7 КБ (+7,5 % к странице), `zod` — 454 КБ.
- Плохо: тип TypeScript и функция разбора — две записи, их нужно менять вместе. Новое правило поля пишется в `readFields` самим.
- Нейтрально: правила с условием записываются обычным кодом, без размеченных объединений и `refine`.

**Подтверждение.** Юнит-тесты `tests/domain/entities.test.ts`: допустимые данные, каждое правило поля, лишние поля для всех шести функций.

## Известные проблемы

### Разные правила проверки одной сущности

**Статус:** снято: форма, загрузка и импорт проверяют записи функциями `parseGpu`, `parseCamera`, `parseDetector` (#48). Импорт файла с GPU без цены отклоняется, загрузка пропускает такую запись (`tests/smoke.test.js`).

Свой GPU: форма требует имя, TFLOPS, декодеры, память и цену больше нуля (`src/js/05-system-ui.js`, обработчик `gpuForm`). Загрузка из `localStorage` проверяет только `id`, `name` и `tflops > 0` (`load`). Импорт проверяет только, что `customGpus` — массив (`importText`). С камерами и детекторами так же. Возможные последствия GPU без цены или с неизвестной архитектурой: стоимость `NaN` в подборе и ошибка при обращении к `NVDEC_FPS[gpu.arch]`. Найдено чтением кода, в браузере не проверялось.

### Поля объекта `fps` и `ref`

**Статус:** снято: поля и ветка удалены владельцем при выносе расчёта (#35). В файлах экспорта и в `localStorage` их больше нет, старые сохранения с ними загружаются.

Поля `fps` и `ref` объекта (`makeObject` в `src/js/02-state.js`) читает только ветка `obj.model === "custom"` при группировке запусков в `computeType`. Модели с id `"custom"` в коде не найдено, поэтому ветка, похоже, никогда не выполняется. Найдено при переименовании (#31).

### Пустое название объекта в заметках

**Статус:** частично решено в #78. Название объекта теперь берётся из его объекта детекции: у встроенного — `nameKey`, у своего `parseDetectionObject` требует непустое `name`. Поэтому со страницы пустое название в расчёт не приходит. Но `parseSceneObject` по-прежнему принимает пустое `name`, и запасное «Объект» (`objDefault` в `src/i18n/domain-text.ts`) оставлено. Чтобы снять проблему, `domain` должен требовать у объекта непустое название, после чего `objDefault` можно удалить. Поведение сохранено при выносе расчёта (#35).

Если название объекта пустое, в списке вердикта «недостаточно» и «на грани» стоит «Объект» (`objectName` в `src/i18n/domain-text.ts`). В заметках `downscale`, `resolution`, `resolutionNone`, в вердикте «достаточно» и в строке объекта в отчёте выводится пустая строка, например «»: на матрице …». Найдено при переносе текстов, на странице не проверялось.

### Неизвестная подача объекта

**Статус:** снято: `parseSceneObject` принимает только `"full" | "roi" | "tiles"` (#48). Импорт файла с другим значением отклоняется, загрузка пропускает тип камер с таким объектом. Подача, которую разбор не пропустил, до расчёта не доходит.

Значение `feed` объекта из файла импорта или `localStorage` не проверяется. Значение не из `"full" | "roi" | "tiles"` расчёт считает тайлами (`describeFeed` в `src/domain/compute-type/feed.ts`), а текст подачи выводит как «кадр … → … px» с размерами выреза зоны. Найдено чтением кода, на странице не проверялось.
