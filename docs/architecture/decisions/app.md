# Решения: app

Итог по модулю: что действует, что отброшено, что осталось открытым.

## Принятые решения

### Состояние в одном месте, изменения только через действия

**Статус:** принято 2026-10-29, перенос — #49. Состояние, включая параметры системы и тему, лежит в `src/app/store.ts`. Код интерфейса разложен по `src/ui/` в #50. Устройство модуля — в [`../modules/app.md`](../modules/app.md).

**Контекст.** Состояние разбросано по глобальным переменным в четырёх файлах: `cameraTypes`, `activeTypeId` (`src/js/02-state.js`), `customGpus`, `gpuPrices`, `gpuEnabled` (`src/js/01-data.js`), `customCameras`, `customDetectors` (`src/js/03-objects.js`), `report`, `stale` (`src/js/05-system-ui.js`). Менять их может любая функция, в том числе отрисовка: `renderObjects` сам заменяет неизвестную модель объекта на `y26s`. Параметры системы (`efficiency`, `reserve`, `archiveDays`, `gpu`, `gpuCount`) хранятся только в полях формы, и расчёт читает их оттуда.

**Решение.** Решаем: всё состояние лежит в одном объекте в `src/app/store.ts`, включая параметры системы. Меняется оно только через функции-действия (`addGpu`, `deleteCamera`, `updateTypeInput` и т. п.). После действия store пересчитывает результаты через `domain` и уведомляет подписчиков. `ui` подписывается на изменения и вызывает действия, но состояние напрямую не меняет.

**Последствия.**

- Хорошо: видно, кто и как меняет состояние; пересчёт и сохранение происходят в одном месте, а не после каждого обработчика.
- Плохо: на каждое изменение нужно действие, и простое присваивание поля превращается в вызов функции.
- Нейтрально: `calcAll` распадается на пересчёт (в `app`) и отрисовку (в `ui`).

**Подтверждение.** Проверка `grep` из [`modules/app.md`](../modules/app.md#проверки): вне `src/app/` нет присваиваний полям состояния. `tests/golden.txt` не меняется.

### Черновик формы отдельно от проверенных значений

**Статус:** принято 2026-10-29 (#36, #49): черновик типа и параметров системы хранится в store как введён, а вместо результата показывается ошибка ввода. Список полей с ошибкой интерфейс не показывает. Правила — в [`domain.md`](domain.md#недопустимое-число-в-черновике-ошибка-а-не-подстановка).

Встроенные названия хранятся ключом словаря `nameKey`, а текст на языке интерфейса подставляет `ui` через `displayName` из `i18n` (решение владельца 2026-10-29). Так `app` не зависит от `i18n`.

**Контекст.** Пользователь вводит значения посимвольно, и промежуточный ввод может быть недопустимым. Сохранение должно вернуть ровно то, что было введено. Сейчас введённые строки и есть модель, и разбираются они только при расчёте.

**Решение.** Решаем: store хранит черновик полей типа камер строками, как ввёл пользователь. Сохраняется тоже черновик. Перед расчётом черновик проходит через `parse*` из `domain`. Если разбор не прошёл, у типа появляется состояние ошибки со списком полей, и `ui` показывает его вместо результата.

**Последствия.**

- Хорошо: ввод не теряется, а расчёт не видит недопустимых значений.
- Плохо: для типа камер в состоянии два представления — черновик и результат разбора.
- Нейтрально: правила показа ошибки решаются в #36.

**Подтверждение.** Тест: недопустимое значение поля даёт ошибку типа, а после перезагрузки страницы введённая строка сохраняется.

### Загрузка и импорт через функции разбора сущностей

**Статус:** принято 2026-10-29, перенос в `src/app/persistence.ts` — #49. Импорт отклоняет файл с недопустимой записью с #36.

**Контекст.** Импорт проверяет только форму файла: что есть массивы и объекты (`importText` в `src/js/05-system-ui.js`). Загрузка из `localStorage` проверяет записи своими условиями и выбрасывает неподходящие (`load`). Импорт сначала проверяет файл и только потом записывает его, чтобы битый файл не стёр сохранённые данные (#3).

**Решение.** Решаем: `src/app/persistence.ts` разбирает сохранение и файл импорта функциями `parse*` из `domain`. Импорт отклоняет файл целиком, если хоть одна запись не проходит разбор, и ничего не записывает. Загрузка из `localStorage` пропускает неподходящие записи, как сейчас.

**Последствия.**

- Хорошо: в сохранение и в расчёт не попадают записи, которые форма бы не приняла.
- Плохо: файлы, которые сейчас импортируются, могут перестать импортироваться, если в них есть записи с нарушениями.
- Нейтрально: формат файла не меняется.

**Подтверждение.** Тесты: файл с одной недопустимой записью отклоняется, сохранённые данные не меняются; сохранение с недопустимой записью загружается без неё.

### Объект типа ссылается на объект детекции по id

**Статус:** принято 2026-10-29, решение владельца в #78.

**Контекст.** До #78 у каждого объекта типа камер были свои габариты, порог и название, а встроенные значения подставляли кнопки-пресеты под списком объектов. Свой шаблон объекта завести было нельзя. В #78 появилась сущность «объект детекции» (`DetectionObject`) с вкладкой на экране шаблонов, а карточка объекта в расчёте стала «детектором»: объект детекции и модель выбираются из шаблонов. Карточка могла бы хранить либо ссылку на шаблон, либо копию его значений на момент выбора. Модель объект уже хранил ссылкой (`model` — id модели).

**Решение.** Решаем: черновик объекта хранит ссылку `target` — id объекта детекции, а габариты, порог и название не хранит. Перед разбором их подставляет `withTargets` в `src/app/store.ts`; `domain` по-прежнему получает `SceneObject` с габаритами и об объектах детекции не знает. При удалении своего объекта детекции объекты с ним переходят на «Человек» (`person`); при загрузке сохранения ссылка на объект, которого нет, — тоже.

**Последствия.**

- Хорошо: правка шаблона сразу меняет расчёт всех объектов, которые его ищут; габарит не расходится между карточками; ссылка устроена так же, как ссылка на модель.
- Плохо: поправить габарит для одной карточки нельзя — нужен отдельный шаблон. Удаление шаблона молча меняет расчёт: объект начинает искать человека.
- Нейтрально: в карточке нет полей габаритов и порога; в сохранении у объекта `target` вместо четырёх чисел и названия.

**Подтверждение.** `tests/page/templates.test.js`: удаление своего объекта детекции переводит карточки на «Человек»; `tests/page/export-import.test.js`: загрузка своего объекта детекции, ссылка на объект, которого нет, заменяется на «Человек». `tests/golden/golden.txt` изменился только из-за примера «Тележка»: он ищет гайку M8 тайлами вместо ячейки ложемента.

### Старые сохранения не переносятся

**Статус:** принято 2026-10-29, решение владельца в #78.

**Контекст.** В #78 поменялся формат данных: свои детекторы стали своими моделями (`customDetectors` → `customModels`), появился список `customObjects`, у объекта типа вместо габаритов — ссылка `target`. Калькулятором пока никто не пользуется, сохранений и файлов экспорта у пользователей нет.

**Решение.** Решаем: перенос старого формата не пишем. Ключ `localStorage` сменён на `camcalc5`, сохранение под `camcalc4` не читается. Импорт требует списков `customModels` и `customObjects` и файл старого формата отклоняет целиком.

**Последствия.**

- Хорошо: в `src/app/persistence.ts` нет кода переноса и проверок старых полей.
- Плохо: если старые данные у кого-то есть, после обновления они не откроются, и свои детекторы и объекты придётся завести заново.
- Нейтрально: следующая смена формата снова потребует решения — переносить или менять ключ.

**Подтверждение.** `tests/page/export-import.test.js`: файл без `customObjects` не импортируется.
