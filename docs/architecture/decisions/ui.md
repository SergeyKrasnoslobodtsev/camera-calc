# Решения: ui

Итог по модулю: что действует, что отброшено, что осталось открытым. Ход поиска — в [`../discussions/ui.md`](../discussions/ui.md).

## Принятые решения

### Интерфейс на React

**Статус:** принято владельцем проекта 2026-10-29. Переход — отдельная задача после #50. Замер, на который опирается решение, — в [`../discussions/ui.md`](../discussions/ui.md).

**Контекст.** После раскладки по `src/ui/` (#50) интерфейс занимает 1703 строки. Разметка собирается шаблонными строками в `innerHTML` (30 мест), 5 функций пересоздают разметку и заново навешивают обработчики, поля формы и состояние синхронизируются вручную (`writeForm`, `readForm`, `syncFormUI`, `writeSystemForm`). Это своё решение задач, которые фреймворки решают отлаженным и общеизвестным способом. Страница должна оставаться одним HTML-файлом, который открывается без сервера.

**Решение.** Решаем: интерфейс пишется компонентами React на TypeScript (`.tsx`). esbuild собирает их в тот же единственный `<script>`, `tsc` проверяет компоненты в составе `npm test`. Из фреймворков выбран самый распространённый: по опросу Stack Overflow 2025 года React используют 44,7% ответивших, Angular — 18,2%, Vue — 17,6%, Svelte — 7,2%. Preact (тот же способ писать компоненты при меньшем размере), Svelte, Solid, Vue и Lit на этом проекте не пробовали.

**Последствия.**

- Хорошо: отрисовка по состоянию вместо ручной работы с DOM; код читается любым разработчиком, знакомым с React; больше всего документации и готовых решений.
- Плохо: новая зависимость в коде страницы, страница становится больше (насколько — не измерено); переписывается весь `ui`.
- Нейтрально: `domain`, `app` и `i18n` от React не зависят и не меняются.

**Подтверждение.** Будет проверено при переходе: `dist/camera-calc.html` остаётся одним файлом и открывается из файловой системы, `npm test` проходит, `tests/golden.txt` не меняется.

### Раскладка `src/ui/` по частям экрана

**Статус:** принято владельцем проекта 2026-10-29, переход — по шагам #65.

**Контекст.** После #50 в `src/ui/` 20 файлов в одной папке: компоненты, вспомогательные функции для DOM, отчёт, маршрутизация, уведомления. Интерфейс переходит на React, и владелец хочет, чтобы структура была привычной для разработчиков на React. Правило проекта требовало имён файлов в kebab-case, а в React-проектах файл компонента обычно называют по имени компонента.

**Решение.** Решаем: `src/ui/` делится на папки по частям экрана (`header/`, `calculation/`, `templates/`), общие компоненты (`components/`), хуки (`hooks/`) и функции без React (`lib/`); целевая раскладка — в [`../modules/ui.md`](../modules/ui.md#раскладка). Файл компонента называется как компонент, файл хука — как хук, остальные файлы — в kebab-case. Старые файлы не переносятся отдельно: каждый шаг #65 кладёт новый компонент на его место и удаляет старый файл.

**Последствия.**

- Хорошо: по папке видно, к какой части экрана относится код; имена файлов совпадают с именами компонентов.
- Плохо: до конца перехода в корне `src/ui/` остаются старые файлы рядом с новыми папками.
- Нейтрально: правило имён в `ARCHITECTURE.md` дополнено исключением для компонентов и хуков.

**Подтверждение.** После #65 в корне `src/ui/` нет файлов, кроме `App.tsx`. Сейчас по раскладке лежат `calculation/TypeTabs.tsx`, `calculation/type-result/`, `calculation/system/`, `templates/GpuParams.tsx`, `components/Tip.tsx` и `hooks/useComputed.ts`; `npm test` проходит. Поля КПД и резерва стоят на экране видеокарт, поэтому их компонент `GpuParams` лежит в `templates/`, а не в `calculation/system/`.

### Интерфейс без фреймворка

**Статус:** отклонено владельцем проекта, заменено решением «Интерфейс на React» (2026-10-29). Было предложено 2026-10-28, замер — в [`../discussions/ui.md`](../discussions/ui.md).

**Контекст.** Интерфейс построен на шаблонных строках: разметка задаётся через `innerHTML`, после каждой отрисовки обработчики событий навешиваются заново (`renderObjects`, `renderGpuView`, `renderCamView`, `renderDetView`). Страница должна открываться из файла без сервера. Владелец проекта знает JavaScript не глубоко.

**Решение.** Решаем: при переходе на новую структуру фреймворк не подключаем. Каждый экран и блок — свой файл в `src/ui/` с функцией отрисовки по состоянию из `app`. Тексты берутся из `i18n`.

**Последствия.**

- Хорошо: нет новой зависимости и нового синтаксиса; переход меняет раскладку кода, а не способ отрисовки.
- Плохо: DOM по-прежнему обновляется вручную, обработчики навешиваются заново после каждой отрисовки.
- Нейтрально: если позже понадобится фреймворк, его можно подключить к той же структуре. Модули `domain` и `app` от него не зависят.

**Подтверждение.** `tests/golden.txt` и smoke-тесты не меняются.

### Текстовый отчёт отдельно от главного цикла

**Статус:** принято 2026-10-29, сделано в #49 и #50. Целевая структура одобрена владельцем 2026-10-28.

**Контекст.** Отчёт для копирования собирается внутри `calcAll` (`src/js/05-system-ui.js`) и хранится в глобальной переменной `report`. Тесты читают его оттуда.

**Решение.** Решаем: отчёт строит функция в `src/ui/report.ts` из результатов расчёта и `i18n`. Вызывается она при нажатии «Копировать отчёт».

Сделано в #49: отчёт строит `reportText` по нажатию, глобальной переменной `report` больше нет. В #50 `reportText` перенесён в `src/ui/report.ts` и получает результаты расчёта параметром.

**Последствия.**

- Хорошо: отчёт не пересобирается при каждом изменении поля, и для него не нужна глобальная переменная.
- Плохо: тесты должны получать отчёт иначе (см. [`build.md`](build.md#тесты-проверяют-страницу-а-не-глобальные-переменные)).
- Нейтрально: текст отчёта не меняется.

**Подтверждение.** `tests/golden.txt` не меняется. Проверено в #50: `npm test` проходит, `git diff tests/golden.txt` пуст, тест страницы получает отчёт через кнопку «Копировать отчёт».
