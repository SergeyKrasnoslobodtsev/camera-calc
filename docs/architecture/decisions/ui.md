# Решения: ui

Итог по модулю: что действует, что отброшено, что осталось открытым. Ход поиска — в [`../discussions/ui.md`](../discussions/ui.md).

## Принятые решения

### Экран расчёта: список типов, шторка и единая сводка

**Статус:** предложено 2026-10-30 в #83 по варианту D макета; ждёт проверки владельцем по снимкам в PR. Своя прокрутка списка типов и раскрытие строки до моделей решены владельцем.

**Контекст.** Вкладки типов неудобны, когда типов много. На телефоне поле ввода и результат его изменения не видны одновременно. Итоги системы и нагрузка на GPU разбросаны по разным блокам страницы.

**Решение.** Решаем: одна сводка системы на всех экранах, список типов вместо вкладок, отдельный экран «Система», на телефоне — обзор, экран типа и шторка с вердиктом и тремя числами. Окно 900–1199 px сворачивает список в переключатель. Нагрузка показывается по типам камер, строка раскрывается до объектов и моделей. У строк списка типов своя прокрутка: фильтры и «+ Тип камеры» остаются в окне при любом числе типов. Правила — в [`../modules/ui.md`](../modules/ui.md#компоновка).

Тип «Недостаточно» на телефоне открывается так же, как любой другой: формой при закрытой шторке. Причина, совет и кнопка «Открыть объект» — в открытой шторке. Таблица сети на экране «Система» стоит в правой колонке: в левой при ширине 1440 px обрезается колонка «Всего».

**Последствия.**

- Хорошо: при 20 типах список, фильтры и кнопка добавления в окне; на телефоне число и вердикт видны во время ввода; итоги системы в одном блоке.
- Плохо: полоса списка типов занимает 280 px ширины, колонки ввода и результата уже; появилась подписка на `visualViewport` для шторки над клавиатурой.
- Нейтрально: в `tests/golden/golden.txt` изменились строки «KPI системы», «Легенда» и «Датчики»: эти блоки заменены. Отчёт, таблица сети, вердикт, показатели и схема не изменились.

**Подтверждение.** `npm test` проходит. В Chrome без окна по `dist/index.html` (2026-10-30): нет прокрутки вбок на 390, 899, 900, 1024, 1199, 1200 и 1440 px; на 20 типах в окне 1440 × 900 кнопка «+ Тип камеры» — 840–880 px, список прокручивается внутри; на 390 px поле «Название» видно сразу после перехода из обзора, поля 44 px, шрифт 16 px; ошибок JavaScript нет. На настоящем телефоне шторка с открытой клавиатурой не проверена.

**Отброшено.** Открывать тип «Недостаточно» сразу со шторкой: поведение различалось бы по статусу, и первое поле было бы закрыто. Скрытые старые блоки ради неизменного эталона: лишний код только для теста.

### Компоновка: ввод слева, результат справа

**Статус:** предложено 2026-10-29 в #79, владелец проекта поручил выбрать по общепринятым правилам. В #83 сохранено для ширины от 900 px и заменено шторкой на телефоне.

**Контекст.** Форма типа стояла под результатом: в окне 1440 × 900 поле и результат его изменения одновременно не видны, на телефоне до первого поля около 1300 px прокрутки. Выбор GPU и глубины архива стоял внутри блоков результата. Рассматривались два варианта: А — форма слева, результат справа закреплён; Б — короткая сводка сверху, форма под ней.

**Решение.** Решаем: вариант А. Ввод слева, результат справа — и для типа камер, и для системы (параметры системы | нагрузка и сеть). Результат типа закреплён, пока виден ввод. На узком экране — одна колонка, ввод перед результатом, вкладки типов с точкой статуса закреплены сверху. Итоги системы — полосой над вкладками. Правила компоновки — в [`../modules/ui.md`](../modules/ui.md#компоновка).

**Последствия.**

- Хорошо: при вводе результат виден без прокрутки (в окне 1000 × 800 и больше); на телефоне первое поле — сразу под итогами и вкладками.
- Плохо: на узком экране полный результат типа — под формой; во время ввода виден только статус на вкладке и в карточке объекта.
- Нейтрально: высота схемы ограничена высотой окна, чтобы закреплённый результат помещался.

**Подтверждение.** `npm test` проходит. В Chrome без окна по `dist/index.html` при прокрутке к середине формы верх результата — 12 px от края окна, низ — 597 px в окне 1440 × 900 и 791 px в окне 1000 × 800 (2026-10-29).

**Отброшено.** Вариант Б: сводка сверху показывает только итог, а не показатели и схему, которые меняет поле; при вводе всё равно нужна прокрутка к результату.

### Интерфейс на React

**Статус:** принято владельцем проекта 2026-10-29. Переход — отдельная задача после #50. Замер, на который опирается решение, — в [`../discussions/ui.md`](../discussions/ui.md).

**Контекст.** После раскладки по `src/ui/` (#50) интерфейс занимает 1703 строки. Разметка собирается шаблонными строками в `innerHTML` (30 мест), 5 функций пересоздают разметку и заново навешивают обработчики, поля формы и состояние синхронизируются вручную (`writeForm`, `readForm`, `syncFormUI`, `writeSystemForm`). Это своё решение задач, которые фреймворки решают отлаженным и общеизвестным способом. Страница должна оставаться одним HTML-файлом, который открывается без сервера.

**Решение.** Решаем: интерфейс пишется компонентами React на TypeScript (`.tsx`). esbuild собирает их в тот же единственный `<script>`, `tsc` проверяет компоненты в составе `npm test`. Из фреймворков выбран самый распространённый: по опросу Stack Overflow 2025 года React используют 44,7% ответивших, Angular — 18,2%, Vue — 17,6%, Svelte — 7,2%. Preact (тот же способ писать компоненты при меньшем размере), Svelte, Solid, Vue и Lit на этом проекте не пробовали.

**Последствия.**

- Хорошо: отрисовка по состоянию вместо ручной работы с DOM; код читается любым разработчиком, знакомым с React; больше всего документации и готовых решений.
- Плохо: новая зависимость в коде страницы, страница становится больше (насколько — не измерено); переписывается весь `ui`.
- Нейтрально: `domain`, `app` и `i18n` от React не зависят и не меняются.

**Подтверждение.** Проверено в #65 (2026-10-29): весь `ui` — компоненты React, в `src/ui/` нет присваиваний `innerHTML` и `addEventListener` для элементов, которые отрисовывает React; `npm test` проходит, `tests/golden.txt` не изменился, вывод smoke-теста построчно совпадает с выводом до перехода. `dist/index.html` — один файл; размер — в [`../discussions/ui.md`](../discussions/ui.md). `dist/index.html` по `file://` в Chrome 156 без окна (через протокол отладки): экраны расчёта и шаблонов, добавление и удаление шаблонов, цены и участие в подборе, подсказки, тема, удаление типа и импорт с подтверждением работают без ошибок JavaScript (2026-10-29). Эта проверка нашла ошибку, которую jsdom пропустил: `scrollTo` в Chrome возвращает Promise, и эффект прокрутки в `App.tsx` возвращал его React вместо функции очистки; заглушка `scrollTo` в smoke-тесте теперь тоже возвращает Promise.

### Раскладка `src/ui/` по частям экрана

**Статус:** принято владельцем проекта 2026-10-29, переход — по шагам #65.

**Контекст.** После #50 в `src/ui/` 20 файлов в одной папке: компоненты, вспомогательные функции для DOM, отчёт, маршрутизация, уведомления. Интерфейс переходит на React, и владелец хочет, чтобы структура была привычной для разработчиков на React. Правило проекта требовало имён файлов в kebab-case, а в React-проектах файл компонента обычно называют по имени компонента.

**Решение.** Решаем: `src/ui/` делится на папки по частям экрана (`header/`, `calculation/`, `templates/`), общие компоненты (`components/`), хуки (`hooks/`) и функции без React (`lib/`); целевая раскладка — в [`../modules/ui.md`](../modules/ui.md#раскладка). Файл компонента называется как компонент, файл хука — как хук, остальные файлы — в kebab-case. Старые файлы не переносятся отдельно: каждый шаг #65 кладёт новый компонент на его место и удаляет старый файл.

**Последствия.**

- Хорошо: по папке видно, к какой части экрана относится код; имена файлов совпадают с именами компонентов.
- Плохо: до конца перехода в корне `src/ui/` остаются старые файлы рядом с новыми папками.
- Нейтрально: правило имён в `ARCHITECTURE.md` дополнено исключением для компонентов и хуков.

**Подтверждение.** После #65 в корне `src/ui/` один файл — `App.tsx`, остальные лежат по раскладке из [`../modules/ui.md`](../modules/ui.md#раскладка); `npm test` проходит. Отличия от раскладки, задуманной до перехода: поля КПД и резерва стоят на экране видеокарт, поэтому `GpuParams` лежит в `templates/`; экспорт и импорт — кнопки экрана шаблонов, поэтому `file-actions.ts` лежит в `templates/`, а не в `header/`; формы шаблонов — отдельные компоненты (`GpuForm.tsx` и другие) с общим каркасом `TemplateForm.tsx`; экран расчёта собирает `calculation/CalculationPage.tsx`.

### Интерфейс без фреймворка

**Статус:** отклонено владельцем проекта, заменено решением «Интерфейс на React» (2026-10-29). Было предложено 2026-10-28, замер — в [`../discussions/ui.md`](../discussions/ui.md).

**Контекст.** Интерфейс построен на шаблонных строках: разметка задаётся через `innerHTML`, после каждой отрисовки обработчики событий навешиваются заново (`renderObjects`, `renderGpuView`, `renderCamView`, `renderDetView`). Страница должна открываться из файла без сервера. Владелец проекта знает JavaScript не глубоко.

**Решение.** Решаем: при переходе на новую структуру фреймворк не подключаем. Каждый экран и блок — свой файл в `src/ui/` с функцией отрисовки по состоянию из `app`. Тексты берутся из `i18n`.

**Последствия.**

- Хорошо: нет новой зависимости и нового синтаксиса; переход меняет раскладку кода, а не способ отрисовки.
- Плохо: DOM по-прежнему обновляется вручную, обработчики навешиваются заново после каждой отрисовки.
- Нейтрально: если позже понадобится фреймворк, его можно подключить к той же структуре. Модули `domain` и `app` от него не зависят.

**Подтверждение.** `tests/golden.txt` и smoke-тесты не меняются.

### Текстовый отчёт отдельно от главного цикла

**Статус:** принято 2026-10-29, сделано в #49 и #50. Целевая структура одобрена владельцем 2026-10-28.

**Контекст.** Отчёт для копирования собирается внутри `calcAll` (`src/js/05-system-ui.js`) и хранится в глобальной переменной `report`. Тесты читают его оттуда.

**Решение.** Решаем: отчёт строит функция в `src/ui/report.ts` из результатов расчёта и `i18n`. Вызывается она при нажатии «Копировать отчёт».

Сделано в #49: отчёт строит `reportText` по нажатию, глобальной переменной `report` больше нет. В #50 `reportText` перенесён в `src/ui/report.ts` и получает результаты расчёта параметром.

**Последствия.**

- Хорошо: отчёт не пересобирается при каждом изменении поля, и для него не нужна глобальная переменная.
- Плохо: тесты должны получать отчёт иначе (см. [`build.md`](build.md#тесты-проверяют-страницу-а-не-глобальные-переменные)).
- Нейтрально: текст отчёта не меняется.

**Подтверждение.** `tests/golden.txt` не меняется. Проверено в #50: `npm test` проходит, `git diff tests/golden.txt` пуст, тест страницы получает отчёт через кнопку «Копировать отчёт».
